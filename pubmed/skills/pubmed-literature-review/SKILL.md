# PubMed Literature Review — 正確な文献データ収集のためのワークフロー

> **位置づけ**: 本スキルは **PubMedのみ** を検索対象とする文献収集・データ抽出ワークフローである。
> Cochrane / PRISMA / AMSTAR 2 が求める複数データベース検索や試験登録の網羅検索は行わないため、
> 成果物を「系統的レビュー」と呼ぶ場合は、PubMed単独検索であることを限界として明記するよう利用者に伝える
> （rapid review、evidence map、SRのデータ収集段階などの表現が適切）。

## 使用する PubMed MCP ツール

同梱の PubMed MCP サーバー（`pubmed_mcp_server2`）のツールを使う。ツール名の接頭辞は環境により異なる
（プラグイン経由なら `mcp__plugin_pubmed_pubmed__search` など）。現在のセッションのツール一覧から
`search` / `count` / `fetch` / `fetch_batch` 等の名前で終わるものを選ぶ。

| ツール | 本スキルでの用途 |
|---|---|
| `count` | 検索式の件数・`query_translation`・`warnings` の確認 |
| `search` | PMID取得。`retmax`（最大500）/`retstart` でページング、`output_mode`、`filters` |
| `fetch` | 単一PMIDの抄録・書誌（著者・雑誌・年・DOI）を取得（再確認用。最も確実） |
| `fetch_batch` | 複数PMIDの抄録・書誌・MeSH・出版タイプを一括取得（`include_abstract: true`）。5〜6件ずつ使う |
| `convert_ids` / `get_full_text` | PMID→PMCID変換と、PMC収録論文の全文（`sections` で章を限定） |
| `export_to_ris` | 採用文献のRIS出力（文献管理ソフト用） |


## なぜこのスキルが必要か

PubMedから複数論文の数値データを抽出する作業には、**2種類の失敗**が潜む。

**① 捏造（データ切断による数値の取り違え）**: バッチ取得ツール（`fetch_batch`）で多数の論文を
一括取得すると、レスポンスが大きすぎて途中で切断されることがある。切断されたデータの断片から
「それっぽい数値」を推定してしまうと、N数・アウトカム値・P値・有意性判定がすべて誤った表ができあがる。

**② 漏れ（対象文献が多いときの取りこぼし）**: 検索・スクリーニング・抽出の各段で件数を照合しないと、
1件抜けても誰も気づかない。検索の retmax 上限で最初から見えていない、context 飽和で後半の抽出結果が
消える、重複排除で固有文献を巻き添えにする、といった経路で「網羅したつもりで抜けている」状態に陥る。

このスキルは、①を **Phase 3 の逐次原文照合**で、②を **カバレッジ台帳と照合ゲート**で防ぐ
ワークフローを定義する。

## サブエージェント運用ルール（必ず最初に読むこと）

このスキルの作業では、**サブエージェントの使い方を誤ると正確性が崩壊する**。
理由は単純で、**サブエージェントからメインに返るのは「要約された最終報告」だけ**であり、
メインは各抄録の原文を見られない。原文照合こそがこのスキルの命であるため、
データ抽出をサブエージェントに分担させると、このスキルが防ごうとしている
「切断・要約・転記ミスによる数値の取り違え」を自ら持ち込むことになる。

### 原則: 抽出と集計はメイン、検証は補助的にサブ

| フェーズ | 実行主体 | 理由 |
|---|---|---|
| Phase 0 メタ解析要否のAskUser | メイン | 抽出方針を最初に確定する判断工程 |
| Phase 1 検索式設計・count | メイン | 件数判断をユーザーと対話しながら行う |
| Phase 2 PMID取得・スクリーニング | メイン | 採用/除外の判断責任を一本化 |
| **Phase 3 抄録取得・数値抽出** | **メイン（逐次）** | **原文を自分の目で照合する工程。サブに振らない** |
| Phase 4 構造化・自己検証 | メイン | 全データを一箇所に集約しないと整合性確認できない |
| **Phase 4後 独立検証** | **サブエージェント（任意）** | **怪しい論文だけ再取得・照合させるのは有効** |
| Phase 5 出力ファイル生成 | メイン | 検証済みデータからの機械的変換 |

### やってよいサブエージェント利用

- **独立検証エージェント**: Phase 4完了後、抽出結果のうち「怪しい数値の論文」だけを
  別エージェントに渡し、`fetch`（1件ずつ）で再取得させて原文と照合させる。
  メインの抽出結果に対する第三者チェックとして機能し、verification stepと合致する。
- メインの抽出が済んだ**検証済みデータ**を入力に、Excel/PPTX生成を別エージェントに
  任せるのは可（生成は機械的変換のため精度リスクが小さい）。

### やってはいけないサブエージェント利用

- ❌ Phase 3を「PMIDを分割して複数サブエージェントで並列抽出」する。
  各サブは要約しか返さないため、メインは原文照合できず捏造リスクが復活する。
- ❌ 検索からExcel出力まで丸ごと1つのサブエージェントに委譲する。
  途中のcount検証・スクリーニング判断・自己検証がブラックボックス化する。

### ユーザー指示が優先される場合

ユーザーが明示的に「Phase 3も並列で」と指示した場合は従うが、
**その際は精度リスクを一言添えてから実行する**（黙って別のやり方に変えない）。

## カバレッジ台帳（全Phaseを貫く Single Source of Truth）— 大量文献での「漏れ」を防ぐ心臓部

このスキルが防ぐ失敗には**2種類**ある。①**捏造**（数値の取り違え・記憶からの補完）と、
②**漏れ（omission）**（対象文献が多いとき、1件抜けても誰も気づかない）。
Phase 3 の逐次照合は①を防ぐが、②は別の仕組みが要る。それが**カバレッジ台帳**である。

### なぜ台帳が必要か（漏れが起きる4経路）

- **サイレント・ドロップ**: 検索→スクリーニング→抽出の各段で件数照合をしないと、途中で1件消えても検出できない。
- **context 飽和による進捗喪失**: 中間データを context 上の辞書/JSON だけで持つと、200件×多数バッチの後半で
  初期の抽出結果が切り捨てられ、「どこまでやったか」が失われる。
- **検索の取りこぼし**: `count` が250でも `search` の retmax 既定で先頭100件しか返らず、150件が最初から視界の外。
- **重複/和集合の事故**: 複数検索式の union で重複排除する際に固有文献を巻き添えで落とす。

### 台帳の実体: ディスク上のCSVを主台帳にする

作業ディレクトリに `ledger.csv` を1つ作り、**PMID 1件につき1行**で全 Phase の状態を管理する。
**context 上の変数ではなくディスクに書く**のが要点（context が飽和しても失われず、末尾で機械照合できる）。

| 列 | 意味 | いつ埋まるか |
|---|---|---|
| `pmid` | PubMed ID | Phase 2 検索直後 |
| `source_query` | どの検索式で拾ったか（複数式のとき） | Phase 2 |
| `title` | タイトル（スクリーニング判断用） | Phase 2 |
| `status` | `pending`→`included`/`excluded`→`extracted`→`verified` | 各Phaseで更新 |
| `exclude_reason` | 除外理由（excludedのときのみ） | Phase 2 |
| `extracted_at` | 抽出済みバッチ番号や時刻 | Phase 3 |
| `notes` | 手動メモ（怪しい点など） | 任意 |

抽出した数値データ本体は別ファイル（`data.csv` または `data.json`）に持ち、`pmid` で台帳と結合する。
台帳は「進捗と網羅性の管理」、データファイルは「中身」と役割を分ける。

### 運用の鉄則

1. **各バッチ完了ごとに台帳へ追記/更新してディスク保存する**（context にため込まない）。
2. **status を必ず前進させる**。抽出したら `extracted`、検証したら `verified` に更新。
3. **中断・再開に強くする**: 作業再開時はまず `ledger.csv` を読み、`status=pending`/`included` の行だけ処理する。
4. Phase 4 の**照合ゲート**（後述）で、台帳の件数とデータ行数が一致するかを機械照合する。

> **少数件（〜15件程度）で、かつ単発の作業**なら台帳を省略してもよい。
> ただし件数帯の判断（Phase 1-2）で「台帳必須」に該当したら必ず作る。

## Phase 0: メタ解析の要否を確認（最初に必ず実行）

**検索を始める前に、まずユーザーへの質問ツール（Claude Code では `AskUserQuestion`、claude.ai では `ask_user_input`。無ければ選択肢付きの質問文）でユーザーに「メタ解析用のデータも収集するか」を質問する。**
これにより、Phase 3 の抽出フィールドが「まとめ表のみ」か「メタ解析投入可能データも含む」かが
分岐する。後から抽出方針を変えると全論文を取り直すことになるため、必ず最初に確定させる。

### 0-1. 質問の出し方

上記の質問ツールで以下を質問する（モバイルでもタップで答えられるよう選択式にする）：

```
質問1: この文献収集の目的は？
  - 文献まとめ表/スライドのみ（数値の一覧化）
  - メタ解析用のデータも収集する（2x2表・mean/SD/N等を抽出）

（「メタ解析用」を選んだ場合のみ質問2を出す）
質問2: 統合したい主要アウトカムのタイプは？
  - 二値アウトカム（例: ADR、検出率の有無 → イベント数/総数）
  - 連続アウトカム（例: APC、抜去時間 → mean/SD/N）
  - 論文によって両方あり得る（テーマ依存）
```

ユーザーがチャットで既に「メタ解析もする」「forest plot用データが欲しい」等と明言している場合は、
質問1を省略してメタ解析モードで進めてよい（ただしアウトカムタイプは確認する）。

### 0-2. モードの確定

回答に応じて、以降のワークフローを次のどちらかに固定する：

| モード | Phase 3 で抽出するもの | Phase 5 の出力 |
|---|---|---|
| **A. まとめモード**（既定） | 既存の標準フィールド（N, アウトカム, P値, 有意性 等） | まとめ表 Excel / スライド |
| **B. メタ解析モード** | 標準フィールド ＋ **メタ解析用フィールド**（後述） | メタ解析投入可能データ（long/wide形式）＋ まとめ表 |

> **本スキルの責務範囲（重要）**: メタ解析モードでも、本スキルが行うのは
> **「メタ解析に投入できる形式でのデータ収集と整形」までである**。
> 統合効果量・I²・τ²・forest plot の算出は**行わない**（R の `meta`/`metafor`、RevMan、CMA 等に
> 渡す前段のデータセットを作るのがゴール）。ユーザーが統合計算まで望む場合は、
> 「収集データは揃った。統合計算は別途R等で行うが、ここで実施するか？」と確認してから別タスクとする。

## Phase 1: 検索式の設計と検証

### 1-1. MeSH検索式を構築する

ユーザーの要求から、以下の要素を特定して検索式を組み立てる：

- **対象疾患/手技**: MeSH termで指定（例: `"Colonoscopy"[MeSH]`）
- **介入/技術**: MeSH + 自由語の組み合わせ（例: `"Artificial Intelligence"[MeSH] OR "CADe"[tiab]`）
- **研究デザイン**: Publication Typeで限定（例: `"Randomized Controlled Trial"[pt]`）
- **期間**: Date of Publication で指定（例: `"2023/01/01"[dp] : "2026/03/31"[dp]`）

検索式の例：
```
("Colonoscopy"[MeSH] OR "Colorectal Neoplasms"[MeSH])
AND ("Artificial Intelligence"[MeSH] OR "Deep Learning"[MeSH] OR "CADe"[tiab])
AND "Randomized Controlled Trial"[pt]
AND ("2023/01/01"[dp] : "2026/03/31"[dp])
```

### 1-2. count で件数を検証し、運用モードを決める

検索式を実行する前に、`count` ツールで件数を確認する。件数によって「絞り込む」のではなく、
**件数帯ごとに運用のやり方を段階化する**（真の系統的レビューでは無理に絞れないため）。

| 件数帯 | 運用モード | やること |
|---|---|---|
| **0件** | 検索式の見直し | 厳しすぎる → MeSH termの拡大・自由語の追加を検討 |
| **1〜15件** | 逐次・台帳任意 | 個別抄録取得で十分。台帳は省略可（単発作業なら） |
| **16〜80件** | 逐次＋**台帳必須** | `ledger.csv` を作り、バッチごとに追記。進捗表示を必須化 |
| **81〜250件** | 逐次＋**台帳必須＋チェックポイント** | 上記に加え、10バッチごとに件数照合。retmaxのページング取得を確認 |
| **250件超** | **台帳必須＋タイトル自動スクリーニング補助** | 全件抽出は非現実的な場合、ユーザーと「PICO再絞り込み」か「タイトル/抄録スクリーニングで母数を減らす」かを相談。母数確定後は上記の運用に乗せる |

> **重要**: 「200件超は絞り込め」と機械的に切らない。系統的レビューでは網羅性が命であり、
> 絞れないテーマも多い。件数が多いときは**絞るのではなく、台帳と分割取得で漏れなく捌く**方針を優先する。

台帳が必要な件数帯だと判明したら、Phase 2 に進む前に `ledger.csv` を初期化しておく。

### 1-3.（メタ解析モードのみ）統合対象アウトカムを事前定義する

メタ解析モードでは、検索に入る前に「何を統合するのか」を1つ以上、明確に決めておく。
これを決めずに抽出を始めると、論文ごとに違う指標を拾ってしまい、統合できないデータになる。

事前に確定させる項目：

- **統合する主要アウトカム名**（例: ADR = adenoma detection rate）
- **アウトカムタイプ**（二値 or 連続）。Phase 0-1 の質問2の回答を踏まえつつ、
  実際の抄録に合わせて論文ごとに判定する（テーマによって混在し得る）。
- **効果指標の想定**（二値: RR/OR/RD、連続: MD/SMD）。どれを選んでも必要な生データは
  同じ（二値=2x2、連続=mean/SD/N）なので、ここでは生データを揃えると決めるだけでよい。
- **解析対象集団の単位**（per-patient か per-lesion/per-polyp か）。
  論文間でこの単位が混在すると統合が破綻するため、どちらに揃えるかを決めておく。

## Phase 2: 検索の実行とPMIDリスト取得（漏れ防止の第一関門）

`search` ツールで検索を実行し、PMIDのリストを取得する。
この段階の目的は**「count で数えた件数を、1件も落とさず PMID リストに落とし込む」**こと。

### 2-1. 検索の完全性チェック（count == 取得PMID数）

`search` の retmax（1回に返る件数の上限）既定値により、**count が250でも先頭100件しか返らない**ことがある。
これが「最初から視界に入らない漏れ」の最大要因なので、必ず照合する：

1. `count` の件数を記録する（例: 218件）。
2. `search` で取得できた PMID 数を数える。
3. **count > 取得数** なら、retmax を上げるか、`retstart` をずらして**ページング取得**し、
   全件を集める（例: 0-99, 100-199, 200-217 の3回に分けて取得）。
4. 最終的に **ユニークPMID数 == count** になったことを確認してから次へ進む。
   （差が出るのは正常な場合もある＝重複除去後など。差の理由を説明できる状態にする）

### 2-2. 複数検索式のときは重複排除（union）を安全に行う

検索式を複数使う場合（例: 疾患別に分けた等）は、全式の PMID を集めてから**重複排除**する。
このとき、どの式由来かを `source_query` 列に残し、**排除前後の件数を両方記録**する
（「union前 312 → 重複排除後 268」のように）。固有文献を巻き添えで落としていないかの検証根拠になる。

### 2-3. 台帳へ全件を書き込む

取得した全 PMID を `ledger.csv` に `status=pending` で書き込む（Phase 1-2で台帳必須と判定された場合）。
**この時点で台帳の行数 == ユニークPMID数** になっているはず。ここが以降の照合の基準線になる。

### 2-4. スクリーニング（PRISMA準拠で記録を残す）

タイトルと基本情報から、テーマに無関係な論文を除外する：
- 対象外の介入（例: CADe検索なのにロボット手術や薬物療法の論文）
- 対象外のデザイン（例: RCT検索なのにメタアナリシスやレビュー）
- 対象外のアウトカム（例: 検出率の検索なのに費用対効果分析）

**除外は必ず PMID ごとに理由を `exclude_reason` 列に記録する**（後から再現・説明できるように）。
採用は `status=included`、除外は `status=excluded` に更新する。

### 2-5. PRISMA 4カウントを確定してユーザーに報告

スクリーニング完了時、以下の4つの数を台帳から集計して報告する（PRISMA flow diagram にそのまま使える）：

- **Identified**（検索でヒットした総数 = count）
- **Screened**（重複排除後にタイトル選別にかけた数）
- **Excluded**（除外数、主要な除外理由の内訳とともに）
- **Included**（本文抽出に進む採用数）

この `Included` 件数が、Phase 4 の照合ゲートで「抽出済み行数と一致すべき目標値」になる。

## Phase 3: 抄録の個別取得（最重要フェーズ）

### 絶対原則: バッチ取得でJSONを丸ごと読もうとしない

> **`fetch_batch` で20件以上を一度に取得すると、レスポンスが途中で切れるリスクがある。**
> 切断されたデータから数値を「推定」「補完」「記憶から引用」することは絶対に禁止する。
> 抄録に明示的に書かれていない数値は「記載なし」とする。

> **このフェーズはサブエージェントに分担させない。** メイン自身が原文を逐語的に照合する。
> （理由は冒頭「サブエージェント運用ルール」を参照）

### 推奨取得方法

**方法A: `fetch_batch`（`include_abstract: true`）で5-6件ずつ取得（推奨）**

`fetch_batch` は指定PMIDの抄録・書誌・MeSH・出版タイプをJSONで返す。**返却件数が要求したPMID数と一致するか必ず確認する**（欠落分は `fetch` で個別に再取得し、取れなければ「取得できなかった」と記録する）。
5-6件ずつのバッチで取得し、各バッチの内容を完全に処理してから次のバッチに進む。

```
Batch 1: PMIDs 1-6 → 全文を読み、データを抽出・記録
Batch 2: PMIDs 7-12 → 全文を読み、データを抽出・記録
...
```

**方法B: `fetch` で1件ずつ取得（最も安全だが時間がかかる）**

件数が少ない場合（10件以下）、または方法Aでデータが不完全な場合に使用する。

### 大量文献でのスケール運用（漏れ防止）

件数が多い（台帳必須の帯）ときは、正確性を守る「5-6件ずつ・逐次・メインのみ」の原則は**一切崩さず**、
以下を追加して**漏れと進捗喪失を防ぐ**：

1. **抽出結果は毎バッチごとに `data.csv`（または `data.json`）へ追記し、ディスク保存する。**
   context 上の辞書にため込まない。後半バッチで初期データが context から切り捨てられても失われない。
2. **抽出した PMID は台帳の `status` を `extracted` に更新する**（`extracted_at` にバッチ番号を記録）。
3. **各バッチ完了時に進捗を必ず表示する**。形式例：
   ```
   Batch 7/34 完了 — 抽出済み 42/198（included）、残り 156
   ```
   これにより「どこまで進んだか」が常に見え、途中で件数がずれても即座に気づける。
4. **チェックポイント照合（81件超の帯）**: 10バッチごとに
   「台帳の `extracted` 件数 == data ファイルの行数」を照合する。ずれていたら**その場で原因を特定**してから続行する
   （末尾まで進んでから気づくと手戻りが大きい）。
5. **中断からの再開**: 作業が途切れたら、まず `ledger.csv` を読み込み、`status=included` かつ未 `extracted` の
   PMID だけを対象に再開する。既に `extracted` の行は取り直さない。

### 各抄録から抽出すべきフィールド

以下のフィールドを、**抄録に記載されている文言そのまま**から抽出する：

| フィールド | 説明 | 注意点 |
|---|---|---|
| PMID | PubMed ID | |
| 1st Author | 筆頭著者 | |
| Journal | 雑誌名 | |
| Year | 発刊年 | |
| Study Name | 試験名/略称 | 抄録に記載されていれば |
| N (analyzed) | 解析対象患者数 | 登録数ではなく最終解析対象のN数 |
| Design | 研究デザイン | Parallel / Tandem / Factorial / Multi-arm |
| Intervention | 介入内容 | 具体的なデバイス名・方法 |
| Primary Outcome | 主要評価項目 | 何が primary endpoint か |
| Intervention Result | 介入群の結果 | 抄録記載の数値そのまま |
| Control Result | 対照群の結果 | 抄録記載の数値そのまま |
| P-value / Effect Size | 統計量 | P値、RR、OR、IRR等 |
| Significance | 有意性判定 | Sig / NS / Borderline |
| Key Finding | 主要所見 | 1文で要約 |

### 数値抽出時の鉄則

1. **抄録に書かれている数値だけを使う**。メモリから「たしか…」で補完しない。
2. **Primary outcomeとSecondary outcomeを混同しない**。抄録で"primary outcome"や
   "primary endpoint"と明示されている指標を記録する。
3. **介入群と対照群を取り違えない**。どちらがどちらか、抄録の文脈から慎重に判断する。
   （例: 「ADR was 54.5% in the control group and 50.7% in the CADe group」のように
   対照群の方が高い場合がある）
4. **解析対象N数を使う**。登録数（enrolled）ではなく、最終解析に含まれた数を記録する。
   （例: 「1228 enrolled, 70 excluded → 1158 analyzed」なら1,158を記録）
5. **数値が切り捨てや丸めなしの原文のままか確認する**。

### （メタ解析モードのみ）追加で抽出するフィールド

メタ解析モード（B）では、標準フィールドに加えて**統合計算に直接投入できる生データ**
（二値の2x2、連続の mean/SD/N、効果量+95%CI のフォールバック）を抽出する。
アウトカムタイプごとに必要なフィールドと、率→イベント数の逆算・SDの換算式・`*_source` フラグの付け方は
**`references/meta-analysis-mode.md` を参照**（モードBのときだけ読めばよい）。まとめモード（A）では不要。

## Phase 4: データの構造化と自己検証

### 4-0. 照合ゲート（漏れを機械的に捕まえる関門）— 必ず最初に通す

Phase 4 に入ったら、**個別データの正しさを見る前に、まず「全件が揃っているか」を機械照合する**。
自己検証チェックリスト（4-2）は各行の正しさを見るが、**「そもそも行が足りていないか」は見ない**。
ここが大量文献での漏れを捕まえる最後の関門になる。

台帳を使っている場合、以下を照合する：

- [ ] **`ledger.csv` の `status=included` の件数 == データファイル（data.csv/json）の行数** か？
- [ ] included なのに `status` が `extracted` になっていない PMID はないか？（＝抽出漏れ）
- [ ] データファイルに、included でない（除外したはずの）PMID が紛れていないか？

**一致しなければゲートを通さない。** 不足している PMID を具体的に列挙し、その論文を `fetch` で
取得して抽出をやり直してから、再度このゲートを通す。件数が一致して初めて 4-1 以降に進む。

> 台帳を省略した少数件の場合は、この照合を手動で行う（included としたPMIDリストと抽出済みリストを目視で突き合わせる）。

### 4-1. 中間データ構造の作成

抽出した全データを、Pythonの辞書リストやJSON形式で一旦まとめる。
この段階でExcel/PPTXを作り始めない。まず中間データの正確性を確認する。

### 4-2. 自己検証チェックリスト

出力ファイルを作成する前に、以下を確認する：

- [ ] 各論文のN数は、抄録に記載された解析対象数と一致しているか？
- [ ] Primary outcomeは、抄録で明示的にprimaryと書かれた指標か？
- [ ] 介入群と対照群の数値が入れ替わっていないか？
- [ ] P値と有意性判定（Sig/NS）が整合しているか？
      （p<0.05でNS、p>0.05でSigになっていないか）
- [ ] 抄録に記載のない数値を補完していないか？
      （記載なしなら「NR (not reported)」と明記する）
- [ ] 同一著者の異なる研究を混同していないか？
- [ ] CADe system名はデバイスの正式名称か？

**（メタ解析モードのみ）追加チェック：** 定義の統一・`events ≤ n`・`*_source` フラグ・単位の統一などの
チェック項目は **`references/meta-analysis-mode.md` の「3. Phase 4 追加チェック」を参照**。

特に怪しい場合は、`fetch` で当該論文を再取得して照合する。

### 4-3. 独立検証エージェント（任意・推奨）

件数が多い、または高stakesの集計（学会発表・論文用）では、Phase 4-2の後に
**独立した検証サブエージェントを1つ起動**し、抽出結果のうち以下に該当する論文だけを
原文と照合させる：

- N数が他論文と桁違いに大きい/小さいもの
- Primary outcomeのP値とSignificance判定が際どいもの（p≈0.05付近）
- 介入群 < 対照群となっている「直感に反する」結果

検証エージェントには「抽出済みの表」と「対象PMIDリスト」を渡し、
`fetch` で再取得して食い違いだけを報告させる。
メインはその報告を受けて、食い違った箇所のみ原文を自分で再確認して修正する。

## Phase 5: 出力ファイルの生成

中間データが検証済みであること（照合ゲートを通過したこと）を確認した上で、ユーザーが要求した形式で出力する。

### 網羅性の記録も併せて出力する

まとめ表・スライドに加え、**PRISMA 4カウント**（Identified / Screened / Excluded / Included）を
出力に含める。学会・論文では PRISMA flow diagram の作成に必須で、再現性の担保にもなる。
台帳（`ledger.csv`）も成果物として残し、除外理由付きで「何を見て何を落としたか」を追えるようにする。

### Excel出力時

- ヘッダー行にフィルター・フリーズペインを適用
- Significance列に色分け（Sig=緑, NS=赤, Borderline=黄）
- 「Key Finding」列はwrap_textで十分な列幅を確保
- 各PMIDにPubMedへのハイパーリンクを付与

### PPTX出力時

- 表スライドでは、抄録から確認済みの数値のみを記載
- 数値が多い場合、Significant / Non-significant に分けたスライドを作成
- Key Takeaways スライドには具体的な数値を引用
- 引用は「Author Year」形式で、具体的数値とともに記載

### （メタ解析モードのみ）メタ解析投入可能データの出力

メタ解析モードでは、まとめ表に加えて**統合ソフトにそのまま読み込める整形済みデータ**
（二値・連続・効果量フォールバックの3種の整形シート/CSV）を出力する。
列定義・`study_id` の付け方・R/RevMan 対応・出力後のユーザーへの一言は
**`references/meta-analysis-mode.md` の「4. Phase 5 メタ解析投入可能データの出力仕様」を参照**。
統合計算（pooled推定・forest plot）は本スキルの範囲外。

### 引用表記ルール（ユーザー設定に従う）

テキスト内で文献に言及する際は、1st author, 雑誌名, 発刊年を記載し、
PubMedへのハイパーリンク (`https://pubmed.ncbi.nlm.nih.gov/{PMID}/`) を付ける：

```
[Lau LHS, Clin Gastroenterol Hepatol, 2023](https://pubmed.ncbi.nlm.nih.gov/37918685/)
```

Excel内のPMID列にも同様にハイパーリンクを埋め込む：
```python
# openpyxlの場合
cell.value = '=HYPERLINK("https://pubmed.ncbi.nlm.nih.gov/37918685/", 37918685)'
```

## アンチパターン集（やってはいけないこと）

以下は、過去に発生した実際のエラーパターンである。これらを避けることがこのスキルの存在意義。

### 0. データ抽出をサブエージェントに並列分担する

❌ PMIDを10件ずつ3つのサブエージェントに分けて並列抽出 → 各サブは要約しか返さず、
   メインは原文照合できないまま3つの報告を結合 → 切断・取り違えが検出されないまま表が完成

✅ 抽出はメインが逐次処理し、検証だけ独立サブエージェントで補助する
   （冒頭「サブエージェント運用ルール」参照）

### 1. バッチ取得の切断を無視する

❌ `fetch_batch` で30件取得 → "Output too large (72.8KB)" → 先頭数件しか読めていない
   のに、残りの論文の数値を記憶やそれらしい推定で埋める

✅ `fetch_batch` で5-6件ずつ取得 → 各バッチを完全に読み取り → データ抽出

### 2. Primary と Secondary の混同

❌ [Spada C, United Eur Gastroenterol J, 2026](https://pubmed.ncbi.nlm.nih.gov/41563802/):
   「ADR 67.6% vs 59.8% p=0.012 → Sig」と記録
   （実際のPrimary endpointはAADR 21.3% vs 20.5% p=0.794 → NS）

✅ 抄録で "primary endpoint was AADR" と明記されている → AADR をPrimary列に記録

### 3. 介入群と対照群の取り違え

❌ [Yabuuchi Y, Dig Endosc, 2025](https://pubmed.ncbi.nlm.nih.gov/40611562/):
   「CADe ADR 53.5% vs Control 48.3% → Sig」
   （実際は Control 54.5% vs CADe 50.7% → NS、CADe群の方が低い）

✅ 抄録原文 "ADR was 54.5% in the control group and 50.7% in the CADe group" →
   Control が高いことを正確に記録

### 4. N数の間違い（登録数 vs 解析数、桁違い）

❌ [Xu X, Surg Endosc, 2025](https://pubmed.ncbi.nlm.nih.gov/40897874/): N=2,128（実際は N=390）
   [Maas MHJ, Endoscopy, 2024](https://pubmed.ncbi.nlm.nih.gov/38749482/): N=3,602（実際は N=497）
   [Gimeno-Garcia AZ, Gastrointest Endosc, 2023](https://pubmed.ncbi.nlm.nih.gov/36228695/): N=2,230（実際は N=370）

✅ 抄録の "included in the final analysis" や "analyzed" の数字を使う

### 5. 有意性の誤判定

❌ [Thiruvengadam NR, Clin Gastroenterol Hepatol, 2024](https://pubmed.ncbi.nlm.nih.gov/38437999/):
   「ADR 40.1% vs 37.7% p=0.36 → NS」
   （実際は ADR 42.5% vs 34.4% p=0.005 → Sig）

✅ 抄録のP値をそのまま転記し、p<0.05ならSig、p≥0.05ならNSと機械的に判定

### 6. 大量文献での「漏れ」を見逃す

❌ count で 218件 → `search` が先頭100件しか返さなかったのに気づかず、100件を「全件」として処理
   → 118件が最初から集計に入らないまま「網羅した」と報告

❌ 150件を逐次抽出中、context 飽和で初期バッチの抽出結果が消失 → 最終Excelが127行しかないのに
   included が150件だったことに誰も気づかない

✅ Phase 2 で count == 取得PMID数 を照合（不足ならページング取得）。
   `ledger.csv` に全件を書き、毎バッチ `data.csv` へ追記。
   Phase 4-0 の照合ゲートで included件数 == データ行数 を機械照合してから出力

## まとめ: ワークフロー全体像

```
[Phase 0] AskUser: メタ解析の要否を確認 → モードA/Bを確定        … メイン
     ↓
[Phase 1] MeSH検索式構築 → count で件数帯を判定・運用モード決定   … メイン
     ↓   台帳必須の帯なら ledger.csv を初期化
     ↓   （モードBのみ）統合対象アウトカム・タイプ・単位を事前定義
[Phase 2] search → count==取得数を照合（不足はページング取得）    … メイン
     ↓   重複排除・全件を台帳へ pending で記録
     ↓   タイトルスクリーニング（除外理由を記録）→ PRISMA 4カウント確定
[Phase 3] fetch_batch で5-6件ずつ取得 → 逐語的に数値抽出   … メイン（並列化禁止）
     ↓   毎バッチ data.csv へ追記＋台帳を extracted に更新＋進捗表示
     ↓   （モードBのみ）2x2 / mean・SD・N / 効果量+95%CI も抽出
[Phase 4] 照合ゲート: included件数==データ行数 を機械照合          … メイン
     ↓   通過後、自己検証チェックリストで各行を照合
     ↓ （任意）怪しい論文だけ独立検証                            … サブエージェント
     ↓
[Phase 5] Excel / PPTX / 他の形式で出力（PRISMA 4カウント同梱）   … メイン
         （モードBのみ）統合ソフト投入可能データも出力（統合計算は範囲外）
```

各Phaseの完了をユーザーに報告しながら進めること。
特にPhase 3は最も時間がかかるが、最も重要なフェーズである。ここを省略しない。
**抽出はメイン・検証はサブ**という役割分担を守ることが、このスキルの**正確性（捏造防止）**を担保する。
**カバレッジ台帳と照合ゲート**を守ることが、このスキルの**網羅性（漏れ防止）**を担保する。この2軸を両輪とする。
